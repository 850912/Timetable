# Timetable RC5.6 — Incremental bidirectional sync

## Implemented

- Stable `syncId` for timetable/course/time-slot entities.
- Room migration 5 -> 6 and sync tombstone storage.
- `SyncRecordPayload` / `SyncEnvelope` / `SyncAck` protocol.
- Phone -> Wear incremental Data Layer transfer.
- Wear -> Phone pending-record piggyback in ACK.
- Final ACK handshake so both sides mark records synced only after the peer accepts them.
- LWW comparison: revision, then updatedAt, then deviceId.
- Parent-before-child application order.
- Missing parent records are retained for retry instead of being acknowledged as complete.
- Deleted/unknown entities use sync tombstones to prevent resurrection.
- DataItems are deleted only after the complete batch is accepted.

## Important validation note

Room schema export is configured through KSP. This source snapshot contains the historical schema files through version 3; versions 4–6 should be generated by the project's GitHub/Gradle build and committed before adding a MigrationTestHelper instrumentation test. Runtime migration SQL was independently exercised against SQLite for the 3 -> 6 path.
